# 双向同声传译软件架构设计

设计基准：Windows 桌面、Python 3.12、千问 `qwen3.8-livetranslate-flash-realtime`。官方接口资料核对日期：2026-10-09。

推荐采用一个桌面应用、两条独立音频管线、两个独立实时翻译会话。GUI 与音频处理解耦，源语言识别、翻译和译文语音直接使用实时同传模型的返回结果。

本目录的 `si-architecture.html` 是音频与会话架构图。图中的 WebSocket 关系代表音频上传及文字、音频返回；云端不会直接写入本地虚拟设备，所有采集与播放由本地音频管线执行。

实现更新：按用户要求采用 PySide6 Widgets，不使用 QML。音频设备层使用 Qt Multimedia，原架构图保留为音频路由与会话关系参考；以下技术栈和目录已同步至当前实现。

## 1. 双向音频路由

上行，示例为中文翻译成英语：

```text
真实麦克风
  -> 上行采集、声道转换、流式重采样
  -> 独立 Qwen 会话 U
  -> 返回的译音解码、播放缓冲、设备采样率转换
  -> 虚拟音频线 A 的播放端
  -> A 的录音端
  -> 会议软件麦克风
```

下行，示例为英语翻译成中文：

```text
会议软件扬声器
  -> 虚拟音频线 B 的播放端
  -> B 的录音端
  -> 下行采集、声道转换、流式重采样
  -> 独立 Qwen 会话 D
  -> 返回的译音解码、播放缓冲、设备采样率转换
  -> 真实耳机或扬声器
```

每个方向单独维护连接、目标语种、采集队列、播放队列、字幕状态和重连状态，能够同时运行。两个方向可以共用凭证和配置服务，但不能把两路音频混入一个会话。

### 虚拟设备的实际选择

Windows MVP 使用现成的虚拟音频驱动，如 VB-CABLE A/B 或其他提供两条相互独立虚拟连接的产品。单个 VB-CABLE 通常只提供一条连接，不能直接承担上述两条隔离通道。驱动的安装、授权和分发条件需按供应商要求处理。

以 VB-CABLE A/B 的常见命名为例：

| 设置位置 | 选择的端点 | 操作 |
| --- | --- | --- |
| 本应用上行输入 | 真实麦克风 | 录音 |
| 本应用上行输出 | `CABLE-A Input` | 播放译音，写入 A |
| 会议软件麦克风 | `CABLE-A Output` | 读取 A |
| 会议软件扬声器 | `CABLE-B Input` | 播放远端原音，写入 B |
| 本应用下行输入 | `CABLE-B Output` | 读取 B |
| 本应用下行输出 | 真实耳机或扬声器 | 播放译音 |

驱动名称中的 Input/Output 是相对于虚拟音频线而言。应用向播放端写入，另一端作为录音设备读取；GUI 应直接显示“写入端 / 采集端”和用途，避免仅依赖设备名称判断方向。

设备管理器需要枚举 Windows 音频端点，检查录音/播放能力、支持的格式及设备是否可用，保存稳定的端点标识和驱动信息。运行时的设备序号可能因重插、重启而变化，不适合作为永久配置。底层库若仅暴露临时索引，应另行建立 Windows 端点标识与当前索引的映射。

会议软件直接选择对应虚拟端点。不要依赖系统默认设备或“立体声混音”实现会议采集，否则通知声、其他应用声音或本应用译音可能一起进入下行。

## 2. 软件分层与技术栈

| 层 | 建议技术 | 职责 |
| --- | --- | --- |
| GUI | PySide6 Widgets + QtAwesome 图标 | 设备选择、启停、音量、字幕、状态反馈 |
| 应用控制 | Python 控制器、Qt 信号槽 | 配置校验、协调两路会话、应用状态 |
| 音频设备 | Qt Multimedia 的 QAudioSource / QAudioSink / QMediaDevices | 枚举稳定设备 ID、录音、播放、设备丢失处理 |
| 音频转换 | NumPy + libsoxr 的流式重采样封装 | 声道转换、采样率转换、格式转换 |
| 模型适配 | `websockets` + `asyncio`，封装 Qwen 3.8 协议 | WebSocket 连接、配置、音频发送、事件接收 |
| 字幕模型 | 独立的事件归并与显示模型 | 原文/译文增量、最终结果、关联、去重 |
| 配置与凭证 | JSON 配置 + Windows 凭据管理器/keyring | 保存端点、语言、展示选项及个人 API Key |

先采用单进程桌面架构。当前需求无需额外 Web 服务、数据库或微服务。音频后端保留接口边界，后续有明确的崩溃隔离或原生 AEC 需求时，再迁移到独立进程。

### 线程与异步运行方式

1. Qt 主线程只处理 GUI、视图模型和用户命令。
2. 一个工作线程运行 asyncio 事件循环，同时管理 U/D 两个会话；每个会话有独立的发送和接收任务。
3. 音频对象和采集/播放定时器位于专用 QThread，使用 Qt Multimedia 支持的设备原生格式。音频线程不执行网络请求、JSON/Base64 编码、文件写入或 GUI 操作。
4. 采集和播放通过有界、线程安全缓冲区衔接；不能从音频线程直接操作 `asyncio.Queue`。跨线程命令使用事件循环的线程安全提交接口。
5. 后端通过 Qt 排队信号通知 GUI；字幕刷新合并到约 10-20 次/秒，减少逐片段刷新的开销。

核心接口可以围绕 `AudioSource`、`AudioSink`、`TranslationSession` 和 `DuplexController` 定义。上行、下行复用同一管线实现，只传入不同的输入、输出和目标语种。

## 3. Qwen 3.8 接入契约

### 连接及格式

北京地域文档给出的 WebSocket 地址为：

```text
wss://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api-ws/v1/realtime?model=qwen3.8-livetranslate-flash-realtime
```

以 `Authorization: Bearer <API_KEY>` 鉴权。地域、业务空间与凭证必须匹配，并作为设置项管理。新加坡地域使用文档列出的对应域名。

默认输入为无文件头、单声道、16 位 PCM，16000 Hz；默认输出为单声道、16 位 PCM，24000 Hz。连接后读取 `session.created`，发送 `session.update`，等待 `session.updated` 确认，再开始传送音频。以服务端确认的格式为准，不能只改变设备采样率标签而不重采样。

上行最小配置：

```json
{
  "type": "session.update",
  "session": {
    "output_modalities": ["text", "audio"],
    "translation": {"language": "en"}
  }
}
```

下行建立另一条连接，将 `translation.language` 配置为 `zh`。源语种可以自动识别；不要直接套用旧版的源语种、音色和 VAD 参数结构。

每路独立保存 `voice`，默认 Tina；会话中以 `session.audio.output.voice` 配置，不能发送旧版顶层 `session.voice`。等待 `session.updated` 后核对返回的 `audio.output.voice` 与请求一致，再启动采集。服务端拒绝或未采用音色时终止该方向并记录错误。音色仅在开始新会话时设置，运行期间锁定菜单，暂停后的恢复和自动重连均沿用该方向的配置。

已于 2026-10-09 在北京地域对 qwen3.8 API 做无音频配置验证：Tina、Serena、Ethan、Maia、Katerina、Ryan、Theo Calm 均获得匹配的服务端确认。GUI 将音色菜单与目标语言放在同一行，旧版配置加载时补充默认音色。此验证确认参数被接受，不代替实际音色听感与会议链路验收。

3.8 的说话人检测使用 `session.audio.input.turn_detection`，默认 `speaker_detection`；同时提供 `server_vad`。先验证默认流式行为，再按会议场景调整。不要照搬 3.5 的顶层 `turn_detection` 或固定等整句结束才发起翻译的流程。

### 需要处理的事件

| 事件 | 本地处理 |
| --- | --- |
| `session.created` / `session.updated` | 记录并确认会话配置、格式和状态 |
| `input_audio_buffer.append` | 客户端发送 Base64 编码的 PCM 音频 |
| `conversation.item.input_audio_transcription.delta` | 累加原文识别增量 |
| `conversation.item.input_audio_transcription.completed` | 以 `transcript` 收敛原文最终结果 |
| `response.audio_transcript.delta` | 音频+文本模式下累加译文增量 |
| `response.text.delta` | 仅文本模式下累加译文增量 |
| `response.audio_transcript.done` / `response.text.done` | 用最终文本收敛当前段，不重复追加整段 |
| `response.audio.delta` | 解码译音，送入对应方向的播放缓冲 |
| `input_audio_buffer.speech_started` | 记录语音起点、原文项 ID 和可用的 `speaker_id` |
| `conversation.item.created` | 仅使用 assistant 译文项的 `previous_item_id` 关联原文项，忽略 user 输入项的顺序关系 |
| `response.done` | 检查响应状态和用量；未完成结果不能标记为正常完成 |
| `error` / 转写失败 / 连接关闭 | 更新该方向状态并执行恢复策略 |
| `session.finished` | 结束会话、关闭连接并释放资源 |

3.8 的增量事件使用 `delta`，按接收顺序累加。3.5 的 `text/stash` 处理方式不能直接复用。字幕关联按会话、原文/译文项和响应标识进行，不能假定原文与译文到达顺序一致或拥有相同的 `item_id`。

将供应商事件转为本地的 `SourceTextDelta`、`TranslationTextDelta`、`AudioChunk`、`SegmentFinalized`、`SessionStatus` 和 `UsageUpdated` 等事件，使 GUI 不依赖 API 原始 JSON。

3.8 原文识别始终开启，不支持关闭，官方文档说明识别结果免费。音频输出需要 `output_modalities=["text","audio"]`；文档未提供仅音频的组合。字幕隐藏只在本地生效，不能据此承诺免除译文文本计费。模型价格、配额及会话限制以实际地域和业务空间为准。

官方还提供 AOQ、WebRTC 接入。现有 Python 项目可先使用 WebSocket；若后续重点是弱网体验和原生降噪/回声消除，再比较 AOQ 的 SDK 平台支持与接入成本。

## 4. 文字、音频与运行开关

每条管线分别设置：

| 开关 | 语义 |
| --- | --- |
| 显示原文 | 控制 GUI 与可选字幕浮窗是否显示识别原文 |
| 显示译文 | 控制 GUI 与可选字幕浮窗是否显示译文 |
| 保存原文 | 控制最终识别内容是否写入记录文件 |
| 保存译文 | 控制最终译文是否写入记录文件 |
| 译音静音 | 本地禁止输出译音并清除待播缓存；会话仍然工作，字幕可继续更新 |
| 暂停翻译 | 停止采集上传，清除待播数据；明确暂停期间不提供翻译，并处理恢复时的新会话/缓存 |
| 停止 | 停采集，结束连接，按用户意图处理尾音并释放设备 |

若“文字输出”仅指 GUI，提供显示开关即可；若还包含控制台或文件，则为每种输出渠道增加独立订阅和开关。关闭显示不能自动代表允许落盘，默认不保存音频和文字。

字幕模型保留方向、会话代次、原文项、译文项、说话人、语音时间范围、增量和最终状态。最终结果到达时替换当前段并标为完成，导出只使用最终或明确标注不完整的结果。说话人编号只在相应会话范围内使用，不能当作真实身份。

语音起止事件可用于句段级字幕时间范围；它们不等同于字词级时间对齐。若导出 SRT，需要定义是按源语音时间还是实际译音播放时间出字幕，并记录对应播放时间。

## 5. 延迟、可靠性和回声

### 音频预算

硬件和虚拟驱动常用 44100/48000 Hz，而服务端默认 16000/24000 Hz。设备端按支持的格式打开，在应用内分别执行输入和输出的流式重采样；立体声输入先按明确规则转换为单声道，输出按设备声道要求复制或映射。

建议从 20-40 ms 采集帧、约 100-200 ms 播放抖动缓冲开始测试。发送可以按网络开销合并小帧，官方示例使用 100 ms 音频块。这些是工程初始值，不是 API 保证。

采集队列按音频时长限制，例如初始预算 300-500 ms。持续拥塞时显示故障并重新同步流，记录丢失区间，避免积压几分钟后再翻译。播放端欠载时补静音；译音积压要按响应/段落整体处理，不能随意丢弃中间 PCM 帧而破坏语音。区分正常的语音生成突发与持续延迟，按实际播放落后时间触发恢复。

统计采集时刻、上传等待、首个文字/音频返回、实际播放时刻、队列时长及欠载次数。官方公布的 2.3 秒 LAAL 是模型评测指标，不能直接当作桌面软件的端到端延迟保证。

### 生命周期

每个方向维护 `Idle -> Connecting -> Configuring -> Running -> Stopping -> Idle`，并具有 `Reconnecting` 和 `Error` 状态。两路状态独立，GUI 汇总总体状态。

网络瞬断可指数退避并加入随机抖动；鉴权错误、无权限、无额度等问题进入可解释的错误状态，避免无限重连。重连、切换语言、切换设备和重新启动都增加本地会话代次，迟到的旧回调和译音必须丢弃。

长会议还需考虑服务端的会话时长和上下文上限，不能假定一条连接永久可用。按实际限制在段落边界轮换会话，明确缓冲与切换行为；原始音频只能归属一个有效会话，防止切换时重复翻译。术语表可重设，历史语境能否传入新会话须以接口支持为准，不能承诺自动延续。

设备拔出、默认设备变化、采样率不支持和虚拟驱动缺失都应显示明确状态。不要自动回退到可能形成回流的设备。启动前检测四个应用端点，并允许逐条管线试音。

正常结束可以发送 `session.finish`，在有限时间内等待 `session.finished` 和尾部结果，随后关闭连接。立即停止或紧急静音优先清空待播译音，不能在用户停止后继续向会议播放历史内容。

### 防止回流与声学回声

首先用两条独立虚拟连接阻止数字回流，不开启 Windows“侦听此设备”，不把上行输出作为下行输入，也不把真实扬声器的系统回环录音混入会议采集。

外放时，真实麦克风仍可能拾取下行译音；虚拟设备隔离无法消除这种声学回声。扬声器模式需要可靠的 AEC，使用实际本地播放信号作为参考，优先评估已有 WebRTC AudioProcessing 或适合的原生音频 SDK，不自行实现回声消除算法。

先验证耳机模式的完整双向链路，再验收扬声器模式的回声消除和双方同时发言。不能靠“播放译音时关闭麦克风”实现完整双工，因为它会丢掉同时发言的内容。会议软件的 AEC/降噪也要实测，它看到的是虚拟端点，不能假定它能够处理本机外放译音形成的回声。

## 6. 现代 GUI 设计

使用 PySide6 Widgets，采用成熟控件、布局管理器、Qt 信号槽和统一主题。界面以频繁操作的桌面工具为目标，使用紧凑排布、清晰层级、适度留白、浅色/深色主题，以及青色和绿色区分上下行。不要把操作界面做成营销首页。

主界面布局：

```text
顶部：应用名称 | 总体状态 | 开始/停止 | 紧急静音 | 设置

左侧：音频路由与会话设置       右侧：字幕工作区
  上行                      [双向] [我的发言] [对方发言]
    真实麦克风、虚拟输出         时间、方向、可用的说话人编号
    目标语言、音色、输入电平     原文（按开关显示）
    启停、译音静音、音量         译文（按开关显示）
    原文/译文显示开关            增量更新、最终确认、故障缺口
  下行
    虚拟输入、真实输出
    目标语言、音色、输入电平
    启停、译音静音、音量
    原文/译文显示开关

底部：两路连接状态 | 当前播放积压 | 欠载提示 | 本次 API 用量
```

设备和语言用下拉列表；是否显示字幕、是否保存记录用开关；音量用滑块；字幕视图用分段选择或标签页；试音、刷新设备和设置等工具使用图标按钮与悬停提示。可以后续添加无边框置顶字幕浮窗；当前实现已提供系统托盘控制。

状态需要覆盖未配置、连接中、运行、静音、暂停、重连、设备丢失和错误。两路独立启停，即使某一路故障，另一路仍可使用。设置页提供地域、业务空间、API Key、热词、保存选项和主题；主界面不显示凭证。

关闭字幕不影响语音路由。文字较长时换行，字幕区支持滚动与暂停自动跟随；设备名很长时省略并用提示展示全名。以 1280x720 起做布局验收，同时测试高 DPI、多显示器和键盘操作。

## 7. 实现目录及现有代码迁移

```text
src/si/
  main.py              启动及离线冒烟检查
  controller.py        双向控制器、配置与生命周期
  audio.py             Qt 音频设备、采集、播放及本地设备测试
  audio_buffers.py     线程安全缓冲、PCM 格式转换与流式重采样
  realtime.py          双会话 WebSocket、握手、发送、接收和重连
  protocol.py          3.8 事件归一化与格式协商
  domain.py            配置、状态及应用事件
  transcripts.py       字幕关联、增量归并及可选导出
  storage.py           配置及凭据
  ui/                  Widgets 主窗口、设置、字幕视图、主题与图标
tests/
  test_si_*.py         新应用的协议、音频、控制器、字幕、存储和 GUI 测试
tools/render_ui.py     使用测试字幕验证多尺寸、浅深主题布局
```

项目原有 PyAudio、WebSocket 和 DashScope 调用原型保留。新应用的协议适配与设备处理已分离，两条管线复用相同实现，并由 Widgets GUI 控制。新应用不读取原型中的固定凭证。

当前原型主要以 3.5 会话结构使用 SDK。新应用使用 `websockets` 在独立适配器内直接实现 3.8 文档中的 WebSocket 协议、会话结构和事件，没有将旧 SDK 配置仅替换模型名称后使用。

## 8. 实施与验收顺序

1. 用文件音频验证 3.8 的连接、`session.updated`、原文/译文增量、译音和结束事件。
2. 接通真实麦克风到会话 U，再接通虚拟线 A 到会议输入。
3. 接通会议输出到虚拟线 B、会话 D 和真实耳机，验证同时运行。
4. 加入 GUI 控制、字幕显示、字幕关联及可选导出。
5. 加入断网恢复、设备拔出恢复、拥塞处理与会话代次隔离。
6. 接入并实测扬声器模式 AEC，完成打包和驱动配置体验。

关键验收：双向并发不串音；连续运行内存和延迟不持续增长；设备格式差异没有变速变调；字幕四种显示组合均不影响译音；静音和停止立即阻止待播音频；重连不播放旧内容；扬声器同时发言不形成翻译回环。实际用量和延迟必须通过真实连接及会议软件测试确定。

当前首版已实现双路控制、音频转换、会话恢复、字幕和导出、配置与安全凭据存储、浅深主题及托盘。已通过离线本地 WebSocket、音频缓冲与格式转换、生命周期和 GUI 测试，以及多尺寸界面渲染检查。

尚未进行真实麦克风、计费模型及会议软件端到端验收，也未接入 AEC。文件音频的真实 API 验证、长会议、外放同时发言、高 DPI 和多显示器仍需后续实测。未安装或修改虚拟音频驱动。首次启动保持空闲，不自动采集或连接模型。

此前的架构图已通过 9/9 showcase 校验，0 错误、0 警告；1440x900、1600x1000、1920x1080、2048x1320 均无页面溢出，已人工查看最小和最大尺寸的浅色、深色截图。该图交付摘要和文件哈希见 `si-architecture.receipt.json`，不代表新应用的验收记录。
